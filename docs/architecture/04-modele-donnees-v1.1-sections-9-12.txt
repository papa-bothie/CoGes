9. Migration Alembic V1 → V1.1
Outil unique : Alembic + SQLAlchemy. Flyway et Liquibase ne figurent plus dans la recommandation. Une
seule chaîne de révisions, exécutée en CI sur une base restaurée de production, avec alembic upgrade
head puis alembic downgrade -1 vérifiés à chaque livraison. La révision V1.1 est non destructive : aucune
colonne supprimée, aucun type réduit, aucune donnée perdue. Seule exception assumée : la vue matérialisée
daily_sales_facts est supprimée puis reconstruite comme table, ce qui est sans risque puisqu'elle ne
porte aucune vérité.

 Étape    Opération                        Détail et précaution

 1        Nouveaux types énumérés          CREATE TYPE pour return_refund_status, forecast_type,

                                           GENERATED dans la même migration. Une colonne générée ne
                                           peut pas être modifiée en place. L'ordre compte : les taux
                                           valant 0 après remplissage, les valeurs recalculées sont
                                           identiques aux anciennes.

 5        Alignement de tax_total          UPDATE sales SET tax_total = 0 — les ventes historiques ont
                                           un taux nul, donc total reste inchangé. Contrôle

 6        CMP initial                      SELECT rebuild_product_stock(id) FROM companies : rejoue le
                                           journal et calcule le CMP historique de chaque article.

                                           ouverte, entreprise par entreprise.

 7        Nouvelles tables                 sale_return_refunds, forecasts, insights,
                                           ml_feature_snapshots, avec leurs FK composites et index.

 8        daily_sales_facts                DROP MATERIALIZED VIEW → CREATE TABLE → reconstruction
                                           complète sur l'historique par la requête de 6.1. Aucune
                                           reprise de données de l'ancienne MV : ses chiffres étaient
                                           faux par duplication.

 9        Contraintes et index             inv_reversal_uq, remplacement de l'index d'idempotence par
                                           sa version partielle (DROP INDEX + CREATE UNIQUE INDEX …
                                           WHERE), CHECK de direction sur payments, plafonds de

 10       Fonctions et triggers            cmp_next_avg, inv_check_reversal, inv_apply_movement
                                           (remplace la version V1), rebuild_product_stock, triggers de

                                           INSTEAD NOTHING par les triggers d'immuabilité.

10. Tests d'intégrité indispensables

résultat, soit une exception PostgreSQL précise. Un test qui passerait parce que l'API a vérifié quelque chose
ne vaut rien : tous ces tests attaquent la base directement.

12. Critère final
  « Le modèle V1.1 est-il maintenant suffisamment cohérent pour commencer l'implémentation backend
  FastAPI + PostgreSQL + Alembic sans devoir refaire le schéma sur les mêmes sujets ? »

  Oui — sur les dix sujets corrigés, aucun ne devrait rouvrir le schéma.
  Les quatre décisions ouvertes sont verrouillées et portées par des structures, pas par des intentions. Les
  dix défauts recensés en section 1 sont chacun corrigés par une contrainte, un index ou une table — pas
  par une convention applicative. Les propriétés critiques (isolation, non-négativité du stock, idempotence
  de l'annulation, plafond de remboursement, égalité comptable) sont désormais vérifiables par un test
  SQL qui attaque la base directement, ce qui est le seul critère fiable de non-régression.

minimale ; les avoirs clients, la comptabilité générale, le multi-devises et les variantes sont explicitement hors

Ordre de développement recommandé : (1) socle tenant + RLS + dépendance de contexte, avec T1–T5 et
T36–T37 avant toute autre ligne de code ; (2) référentiels et prix ; (3) stock et CMP, avec T6–T13 et T38 ; (4)

dettes et paiements, T25–T28 ; (7) outbox et couche analytique, T29–T32, T40 ; (8) forecasts et insights, T33–
